# Setpeta - カラオケ配信セトリ作成ツール 要件・設計docs

## 1. 概要

YouTubeで歌枠配信をするVTuber/配信者向けの、Chrome拡張機能。
配信中にカラオケ音源(YouTube動画)を再生するたびに「再生開始時刻」と「動画タイトル」を自動記録し、
配信終了後にアーカイブの1曲目開始タイミングを1回入力するだけで、タイムスタンプ付きセトリを自動生成する。

対象ユーザーは開発者本人(ほぼ自分用)。将来的に無料公開する可能性はあるが、
現時点では認証・課金・サーバー等の複雑さを避け、Chrome拡張単体で完結させる。

## 2. ユースケース(基本フロー)

1. 配信者がYouTubeで歌枠配信を開始する
2. カラオケ音源をYouTubeで再生する(どのYouTubeタブで再生しても自動的に記録される)
3. 再生開始のたびに、拡張が自動で「時刻(ローカル時刻)」+「動画タイトル」+「動画URL」を記録する
4. 記録されたログは拡張のUI(サイドパネル)のログ一覧に追記されていく
5. 配信終了後、配信者はアーカイブを見て「1曲目が実際に何分何秒から始まっているか」を確認する
6. その値を拡張のUIに入力すると、記録済みログとの差分(オフセット)を計算し、
   全曲にアーカイブ基準のタイムスタンプを付与したセトリテキストを生成する
7. 生成されたセトリをコピーして概要欄に貼り付ける

補足: 当初は「記録対象タブ」を明示的に指定する仕組みを検討していたが、
YouTube自体が「別タブで再生を始めると元のタブの再生を自動で一時停止する」仕様のため、
複数タブ同時再生によるログ混入は実運用上ほぼ起こらないと判断し、
タブ指定なしで全YouTubeタブ共通に記録する方式に変更した。

## 3. 非機能要件・前提

- サーバーは持たない。全処理はローカル(ブラウザ内)で完結する
- YouTube API / OAuth連携は使わない(配信開始時刻の自動取得はしない)
  - 理由: 認証の複雑さ、Google審査コストに対して、結局「1曲目開始位置」の手動確認は
    (待機画面・トーク等があるため)API連携があっても不要にならず、恩恵が薄いため
- 配布はChrome Web Store、またはローカル読み込み(開発者モード)を想定。当面は自分用
- Windows/Chrome環境を前提とする

## 4. アーキテクチャ

Chrome拡張機能(Manifest V3)単体で完結。

```
[content script]
  YouTubeの視聴ページ(watch)上で動作
  - メインプレイヤー(#movie_player)配下の<video>のplayイベントのみを監視
    (サムネイルホバー時のプレビュー再生等を除外するため)
  - 再生検知時刻(ts)は即座に取得。動画タイトルはdocument.titleの更新が
    playイベントに追いつかないことがあるため、少し待ってから取得する
  - 動画URL(list/index等を除いた watch?v=ID の形)も取得する
  - 直近のユーザー操作(クリック/キー入力)の有無から、自動再生かどうかを推定する
  - タブの指定なしで、検知結果を都度backgroundに送信

[background (service worker)]
  - content scriptからのイベントを受信し、ログとして chrome.storage に蓄積
  - サイドパネルが閉じていても記録を継続する

[side panel UI]
  - ログ一覧を表示(時刻 + 曲名。自動再生と推定されたものには[自動]バッジ)
  - ログの手動編集(誤検知の削除・曲名修正)に対応
  - 「1曲目のアーカイブ開始時刻」入力欄
  - 入力するとオフセットを計算し、タイムスタンプ付きセトリを生成して表示
  - 生成結果をコピーするボタン
```

## 5. 主要機能の詳細

### 5.1 再生検知
- `#movie_player`配下の`<video>`要素の`play`イベントを対象とする(メインプレイヤー限定。
  サムネイルホバー時のプレビュー再生などはこれで除外される)
- content.js起動より前に自動再生が始まっていた場合(再生リスト選択直後など)に備え、
  起動時点で既に再生中の動画がないかを1回チェックする
- 記録時刻(ts)はplayイベント発火時点で即座に取得する。動画タイトルは
  document.titleの更新がplayイベントに追いつかないことがあるため、0.8秒待ってから取得する
  (タイトル変更の"検知"待ちにすると、再生が短時間に連続した際に取り違えるバグがあったため、
  固定時間待つだけのシンプルな方式にしている)
- タイトル整形時、YouTubeが未読通知件数を先頭に付ける`(2) `のような表記は取り除く
- **「本当に新曲かどうか」の判定はしない**。歌枠では「開く→一時停止→頭出し→本番再生」のように
  同一動画で`play`が複数回発火するのが普通のため、下手に判定ロジックを入れると
  正当な頭出し再生まで弾いてしまうリスクがある
- そのため手動再生の`play`イベントは条件なしで都度そのまま記録する。重複・不要なログは
  5.2の手動削除機能でユーザーが配信後に整理する前提とする
- 記録対象タブの指定は行わない(2章補足を参照)。直近のユーザー操作の有無から
  自動再生かどうかを推定する
- 自動再生(ページを開いた直後の自動再生・プレイリストの次の曲への自動遷移など)と判定した場合、
  設定でユーザーが有効化していれば(既定でON)、配信者の意図しないタイミングで音が出るのを
  防ぐため即座に一時停止し、記録は行わない(配信者が実際に再生ボタンを押した時点で
  あらためて手動再生として記録される)。設定で無効化している場合は従来通り記録する
- YouTubeはwatchページ間の遷移をSPA(pushState)で行うため、遷移のためのクリック自体が
  「直近の操作」として残り続け、遷移直後の自動再生を手動再生と誤認識してしまう問題があった。
  YouTube側が発火する`yt-navigate-start`イベントを合図に操作履歴をリセットして対応している

### 5.2 ログ管理
- 記録項目: ローカル時刻(記録時点)、動画タイトル、動画URL
  (自動再生と判定された再生は5.1の通り記録前に一時停止されるため、ログは常に手動再生分のみ)
- `chrome.storage.local`に永続化し、ブラウザ再起動やサイドパネルの開閉に影響されない
- UI上でログの手動削除・曲名編集ができる(誤検知対応、表記ゆれ修正のため)
- 最後の記録から20時間以上経過していた場合、次にログへアクセスしたタイミング
  (サイドパネルを開く/新規記録が発生する等)で自動的にログをリセットする
  (前回配信分のクリア忘れ対策)

### 5.3 セトリ生成
- 入力: 「1曲目のアーカイブ上の開始時刻」(例: 3:45)
- 計算: ログ上の1曲目時刻とのオフセットを算出し、以降の全曲ログ時刻に同じオフセットを適用
- 出力形式(例):
  ```
  00:00:00 配信開始

  00:00:05 動画タイトルだよ～
  https://www.youtube.com/watch?v=xxxxxxxxxxx

  00:05:05 次の動画タイトル
  https://www.youtube.com/watch?v=yyyyyyyyyyy
  ```
- 出力はテキストエリアに表示し、コピーボタンでクリップボードにコピーできるようにする

## 6. 対象外(やらないこと)

- YouTube Data API / OAuth連携による配信開始時刻・動画メタデータの自動取得
- ローカルexe・常駐アプリ・localhostサーバーの提供
- 課金・ライセンス認証機能
- Chrome以外のブラウザ対応

## 7. 今後の検討事項

- Web Store公開時の権限(host_permissions)説明・プライバシーポリシーの用意
- 誤検知(シーク時の誤ログ等)の実運用での洗い出しと対策
- セトリ出力フォーマットのカスタマイズ(曲名の整形ルールなど)
- 再生を一度も止めずにタブを閉じた場合、最後の1曲が記録されない可能性がある点への対応要否
